# 트랜잭션 ACID와 격리 수준, 그리고 NoSQL의 트레이드오프

## 트랜잭션(Transaction)이란

트랜잭션은 여러 작업을 하나의 논리적 단위로 묶은 것이다. 계좌이체를 예로 들면 "A 계좌에서 출금" + "B 계좌에 입금" 두 작업은 반드시 함께 성공하거나 함께 실패해야 한다. 이 성질을 보장하기 위해 DB는 ACID라는 4가지 원칙을 지킨다.

## 원자성 (Atomicity)

"다 하거나, 하나도 안 하거나(all or nothing)."

트랜잭션 도중 일부 작업만 성공하고 나머지가 실패하면, DB는 이미 성공한 부분까지 전부 되돌려서 트랜잭션이 아예 없었던 것처럼 만든다. 이를 **롤백(Rollback)**이라고 한다.

- 예: A 계좌 출금은 성공했는데 B 계좌 입금 전에 서버가 죽으면 → A 계좌 출금도 취소됨
- 구현 방식: 트랜잭션 시작 전 상태를 로그(undo log 등)에 기록해두고, 문제가 생기면 로그를 보고 원상복구

## 지속성 (Durability)

커밋(commit)이 완료된 트랜잭션은 그 직후 서버가 다운되더라도 결과가 영구히 보존되어야 한다. "커밋됐다"는 DB가 "이 작업은 안전하게 저장됐다"고 사용자에게 한 약속이기 때문이다.

### WAL(Write-Ahead Log)로 지속성 구현하기

문제: 커밋 처리(디스크 쓰기) 도중 정전이 나면 절반만 쓰인 상태가 될 수 있다. 이를 막기 위해 DB는 실제 데이터 파일을 직접 고치기 전에, 변경 내용을 먼저 로그 파일에 순서대로 기록한다.

**동작 흐름:**
1. 트랜잭션 커밋 요청 → 변경 내용을 WAL에 append
2. WAL이 디스크에 fsync 완료 → 이 시점에 "커밋 성공" 응답
3. 실제 테이블 파일 갱신은 그 이후 여유 있게 진행 (성능을 위해 지연)

커밋 도중 정전이 나도 두 경우뿐이다:
- WAL 기록이 디스크에 다 안 써졌다면 → 커밋 응답 자체를 안 보냈을 것 → 재시작 후 미완료로 취급, 롤백
- WAL 기록은 다 써졌는데 테이블 파일 갱신이 안 끝났다면 → 재시작 시 WAL을 다시 읽어 변경을 재적용(**redo**)

즉 "커밋됐다"의 기준은 테이블 파일 갱신 여부가 아니라 **로그가 디스크에 안전하게 남았는가**이다. 로그만 있으면 테이블은 언제든 재구성할 수 있다.

**왜 로그부터 쓰는가:** 테이블 파일은 인덱스가 있고 여러 페이지에 데이터가 흩어져 있어 구조가 복잡하다. 갱신 도중 멈추면 어디까지 썼는지 알기 어렵고 데이터가 깨질 수 있다. 반면 로그는 순서대로 append만 하는 단순한 파일이라 "어디까지 확실히 써졌는지" 검증하기 쉽다(끝의 체크섬/완료 마커만 확인하면 됨). 그리고 테이블 갱신은 로그를 보고 몇 번을 재시도해도 결과가 같은(idempotent) 작업이라 안전하게 미룰 수 있다. 즉 검증하기 쉬운 작업(로그 append)만 커밋 시점의 안전 기준으로 삼고, 복잡한 작업(테이블 갱신)은 뒤로 미루는 전략이다.

## 일관성 (Consistency)

원자성/격리성이 트랜잭션 "실행 과정"을 지키는 것이라면, 일관성은 트랜잭션 실행 **전후의 결과 상태**가 DB의 규칙(제약조건, 무결성)을 위반하지 않는 것을 말한다.

- 예: "잔액은 음수가 될 수 없다"는 규칙이 있을 때, 1000원 잔액에서 1500원 이체를 시도하면 DB는 트랜잭션을 실패시키고 롤백한다. 그 결과 DB는 규칙을 위반하는 상태로 절대 끝나지 않는다.

원자성은 일관성을 지키기 위한 **수단**이다. 규칙 위반이 생기면 롤백해서 위반 상태가 영구히 남지 않도록 막는다.

## 격리성 (Isolation)

동시에 실행되는 여러 트랜잭션이 서로의 **중간 상태(아직 커밋되지 않은 상태)**를 보지 못하게 막는 것이다. 락(lock)이 대표적인 구현 수단이다.

격리성이 부족할 때 발생할 수 있는 문제 3가지:

| 문제 | 설명 |
|---|---|
| Dirty Read | 아직 커밋되지 않은 값을 다른 트랜잭션이 읽어버림. 나중에 원래 트랜잭션이 롤백되면 읽은 값은 애초에 존재한 적 없는 값이 됨 |
| Non-repeatable Read | 이미 커밋된 값이지만, 같은 트랜잭션 안에서 같은 행을 두 번 읽었을 때 값이 다르게 나옴 (그 사이 다른 트랜잭션이 값을 바꾸고 커밋했기 때문) |
| Phantom Read | 같은 조건(WHERE)으로 두 번 조회했는데 행의 개수/집합 자체가 바뀜 (그 사이 다른 트랜잭션이 행을 insert/delete하고 커밋했기 때문) |

Non-repeatable Read와 Phantom Read의 차이: 전자는 **같은 행**의 값이 바뀌는 것, 후자는 조회 결과에 포함되는 **행의 집합**이 바뀌는 것이다.

### 격리 수준(Isolation Level)

DB는 이 3가지 문제를 얼마나 막을지에 따라 4단계 격리 수준을 제공한다. 상위 레벨로 갈수록 하위 문제들을 누적해서 막는다.

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read |
|---|---|---|---|
| READ UNCOMMITTED | 발생 가능 | 발생 가능 | 발생 가능 |
| READ COMMITTED | 막음 | 발생 가능 | 발생 가능 |
| REPEATABLE READ | 막음 | 막음 | 발생 가능 (DB마다 다름) |
| SERIALIZABLE | 막음 | 막음 | 막음 |

- **READ UNCOMMITTED**: 이름이 헷갈리지만 "커밋 안 된 것도 읽는다"는 뜻으로, 아무것도 안 막는 가장 느슨한 단계다.
- **READ COMMITTED**: 커밋된 값만 읽는다 → Dirty Read를 막음
- **REPEATABLE READ**: 반복해서 읽어도 같은 값 → Non-repeatable Read까지 막음
- **SERIALIZABLE**: 트랜잭션들이 순서대로 하나씩 실행된 것처럼 동작 → Phantom Read까지 막음, 가장 엄격하고 가장 느림

위로 갈수록 안전하지만 락을 더 오래/넓게 잡거나 스냅샷을 더 오래 유지해야 해서 동시성 성능이 떨어지는 트레이드오프가 있다.

**실무 기본값:**
- MySQL(InnoDB): REPEATABLE READ (복제, 갭 락 등 InnoDB 고유 설계 때문)
- PostgreSQL, Oracle, SQL Server: READ COMMITTED

업계 전반적으로는 READ COMMITTED가 더 널리 쓰이는 기본값이다. Dirty Read는 거의 모든 상황에서 치명적이라 기본으로 막지만, Non-repeatable Read 정도는 감수 가능하다고 보는 애플리케이션이 많기 때문이다 — "필요한 만큼만 안전하고 나머지는 성능을 위해 양보"하는 절충안인 셈이다.

## NoSQL vs RDBMS: 응답 속도 차이의 이유

"NoSQL이 SQL보다 무조건 빠르다"는 명제는 틀렸다. NoSQL이 빠를 수 있는 경우엔 다음과 같은 구조적 이유가 있다.

1. **조인(JOIN)이 없음** — RDBMS는 정규화된 여러 테이블을 조인해서 데이터를 합치는데 이 비용이 크다. 문서형 NoSQL은 관련 데이터를 애초에 한 덩어리(document)로 **비정규화**해서 저장하므로 조인 없이 한 번에 가져온다.
2. **스키마가 유연함** — RDBMS는 매 쓰기마다 타입/제약조건 검증을 거치지만 NoSQL은 이 검증이 느슨해 쓰기 오버헤드가 적다.
3. **수평 확장이 쉬움** — NoSQL은 여러 서버에 데이터를 쪼개(sharding) 분산 저장하도록 설계된 경우가 많아 서버 추가로 처리량을 늘리기 쉽다.
4. **ACID 보장이 약함** — 원자성/격리성 등을 엄격히 지키지 않는(혹은 단일 문서 단위로만 보장) 대신 락/검증 비용을 줄여 빠르다.

### 비정규화의 대가: Update Anomaly

관련 데이터를 통째로 복사해서 저장하면 읽기는 빨라지지만 수정이 비싸진다.

```json
// order1
{ "customer_name": "김진영", "item": "책" }
// order2
{ "customer_name": "김진영", "item": "노트북" }
```

고객 이름이 바뀌면:
- RDBMS(정규화): `customers` 테이블 1행만 UPDATE
- NoSQL(비정규화): 이 고객이 걸린 모든 문서를 찾아 하나씩 UPDATE 필요

이때 갱신 비용 증가와 불일치 위험(하나라도 갱신을 놓치면 같은 사람인데 이름이 다른 문서가 공존)이 생긴다. 이것이 RDBMS에서 정규화를 하는 이유이기도 하다 — "같은 정보는 한 곳에만" 두면 수정 시 한 번만 고치면 되고 불일치가 원천적으로 불가능하다.

### 절충안: 참조(Reference) 방식

자주 바뀌는 값은 통째로 복사하는 대신 ID만 저장하고, 필요할 때 애플리케이션 레이어에서 별도 조회한다.

```json
// order1
{ "customer_id": "user123", "item": "책" }
// order2
{ "customer_id": "user123", "item": "노트북" }
```

- 완전 비정규화(값 복사): 읽기 빠름, 수정 비쌈
- 참조(ID만 저장): 수정 쉬움(한 곳만 고침), 읽을 때 조회가 한 번 더 필요

결국 DB가 안 해주는 조인을, 애플리케이션 코드가 대신 하는 것이다. 실무에서는 데이터 성격에 따라 섞어 쓴다:

- 거의 안 바뀌는 값(이름 등) → 통째로 복사 (읽기 최적화)
- 자주 바뀌는 값(재고 수량, 잔액 등) → ID만 두고 참조 (일관성 우선)

RDBMS는 정규화가 기본값이라 이런 고민이 덜하지만, NoSQL은 필드마다 "복사할까 참조할까"를 설계자가 매번 판단해야 한다.

## 정리: 언제 무엇을 쓸까

- 쓰기가 잦고 일관성이 중요한 데이터(계좌 잔액 등) → RDBMS가 유리
- 읽기가 압도적으로 많고 웬만해선 안 바뀌는 데이터(로그, 상품 상세페이지 등) → NoSQL 비정규화가 유리
