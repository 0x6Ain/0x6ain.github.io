# 싱글턴 패턴

## 싱글턴 패턴이란

싱글턴(Singleton)은 **어떤 클래스의 인스턴스가 프로그램 전체에서 딱 하나만 존재하도록 보장**하는 디자인 패턴이다. 설정(Config), 로그(Logger), DB 커넥션 풀처럼 "공유되어야 하는 상태/자원"을 다룰 때 흔히 쓰인다.

## 왜 인스턴스를 하나로 제한하는가

인스턴스가 여러 개 존재하면 다음과 같은 문제가 생긴다.

- **Config**: A 모듈이 설정값을 바꿔도 B 모듈이 보는 인스턴스는 그대로일 수 있다 → 어떤 게 진짜 값인지 애매해진다.
- **Logger**: 여러 인스턴스가 각자 파일 핸들을 열면 로그 쓰기 순서가 꼬이거나 파일이 깨질 수 있다.
- **DB 커넥션 풀**: 커넥션은 비싼 자원이다. 인스턴스마다 풀을 새로 만들면 DB에 연결이 과도하게 뚫려 리소스 낭비와 서버 과부하로 이어진다.

즉, **공유되어야 하는 상태를 여러 인스턴스로 쪼개면 일관성이 깨지거나 자원이 낭비된다**.

## 기본 구현: 생성자를 막고 하나의 통로로만 접근

핵심 아이디어는 "생성 로직을 클래스 내부에 가두고, 외부에는 항상 같은 인스턴스만 돌려준다"는 것이다.

```python
class Logger:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
```

사용자는 평소처럼 `Logger()`를 호출하지만, 내부적으로는 이미 만들어진 인스턴스가 있으면 그걸 반환하고, 없으면 그때 만든다.

## 멀티스레드 환경에서의 문제: race condition

위 구현은 `if cls._instance is None:` 체크와 실제 생성 사이에 **타이밍 틈**이 있다. 두 스레드가 동시에 처음 `Logger()`를 호출하면:

1. 스레드 A가 `None` 체크 통과
2. A가 인스턴스를 만들기 전에 B도 같은 체크를 통과 (아직 `None`)
3. A가 인스턴스 생성 → `_instance`에 저장
4. B도 인스턴스 생성 → `_instance`를 덮어씀

결과적으로 인스턴스가 두 번 만들어지고, 이미 이전 인스턴스를 참조 중이던 코드와 상태가 어긋날 수 있다. 이렇게 "체크 후 행동(check-then-act)"이 원자적이지 않을 때 생기는 문제를 **race condition**이라고 한다.

## 해결책 1: 더블 체크 락킹 (Double-Checked Locking)

매번 락을 거는 건 성능 낭비이므로, "처음 생성할 때만 락을 걸고 이미 만들어진 뒤로는 락 없이 반환"하는 구조를 쓴다.

```python
class Logger:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:          # 1차 체크 (락 없음)
            with cls._lock:                 # 락 걸기
                if cls._instance is None:   # 2차 체크 (락 안에서 재확인)
                    cls._instance = super().__new__(cls)
        return cls._instance
```

- **1차 체크**: 이미 인스턴스가 있으면 락 근처도 안 가고 바로 반환 → 평소엔 빠름.
- **락 안의 2차 체크**: 두 스레드가 동시에 1차 체크를 통과해 락 앞에 줄 서도, 먼저 락을 잡은 스레드가 인스턴스를 만들고 나오면 뒤 스레드는 락 안에서 다시 확인해 재생성을 막는다.

## 해결책 2: Eager Initialization

프로그램 시작 시점에 무조건 인스턴스를 만들어버리는 방법. race condition이 생길 여지 자체가 없어 코드가 단순하다.

## Eager vs Lazy 선택 기준

- **Eager**: 인스턴스 생성 비용이 싸고, 프로그램이 거의 항상 그 객체를 쓸 것이 확실할 때.
- **Lazy**: 생성 비용이 비싸거나(DB 커넥션, 큰 리소스 로딩), 어떤 실행 경로에서는 아예 필요 없을 수도 있을 때. 안 쓸 수도 있는 걸 미리 만들면 시작 시간과 메모리가 낭비된다.

한 줄 요약: **"거의 항상 쓴다" → eager, "안 쓸 수도 있다/비싸다" → lazy**.

## 실무 팁

더블 체크 락킹은 코드가 복잡하고 실수하기 쉽다. 실무에서는 대부분 eager를 선호하는데, 요즘 언어들이 언어 차원에서 스레드 안전한 지연 초기화를 이미 보장해주기 때문이다.

- Python: 모듈은 최초 import 시 한 번만 실행되고 이후 캐시된다.
- Java: `static` 초기화 블록은 클래스 로딩 시점에 JVM이 스레드 안전하게 처리한다.
- Kotlin: `object` 선언 자체가 스레드 안전한 싱글턴이다.

따라서 직접 더블 체크 락킹을 구현하기보다, 언어/플랫폼이 제공하는 초기화 보장을 활용하는 것이 낫다.
