# RAG (Retrieval-Augmented Generation)

## 개념

RAG는 LLM이 답을 생성하기 **전에**, 질문과 관련된 문서를 외부 지식
소스에서 **검색(Retrieval)** 해 컨텍스트로 넣어주고, 그 근거를 바탕으로
답을 **생성(Generation)** 하게 하는 구조다. "검색 + 생성"의 결합이라
검색 증강 생성이라고 부른다.

## 왜 필요한가

LLM만으로는 다음 한계가 있다.

- **최신성**: 학습 시점 이후의 정보를 모른다.
- **비공개 데이터**: 사내 문서·DB처럼 학습에 포함되지 않은 내용을
  모른다.
- **환각(Hallucination)**: 모르는 것도 그럴듯하게 지어낸다.
- **출처 부재**: 근거를 제시하지 못한다.

RAG는 답변 시점에 관련 문서를 검색해 컨텍스트로 주입함으로써 이를
보완한다. 모델을 다시 학습(파인튜닝)하지 않고도 지식을 최신으로
유지할 수 있고, 검색된 문서를 출처로 제시할 수 있다.

## 파이프라인

RAG는 크게 두 시점으로 나뉜다.

```
[색인 · 오프라인]
문서 ─(정제/청킹)→ 임베딩 ─→ 벡터 DB 저장

[검색·생성 · 런타임]
질문 ─→ 임베딩 ─→ 벡터 유사도 top-K 검색 ─→ LLM이 근거로 답변 생성
```

1. **색인(Indexing)**: 원본 문서를 검색 텍스트로 가공하고, 필요하면
   문단 단위로 쪼갠 뒤(청킹), 임베딩해서 벡터 DB에 저장한다. 미리
   해두는 배치성 작업이다.
2. **검색(Retrieval)**: 사용자 질문도 같은 방식으로 임베딩한 뒤, 벡터
   유사도로 가장 가까운 문서 K개(top-K)를 가져온다.
3. **생성(Generation)**: 검색된 문서를 컨텍스트로 묶어 LLM에 주고,
   "이 근거 안에서만 답하고 출처를 표시하라"는 식으로 지시해 답변을
   만든다.

## 운영에서 중요한 것: 데이터 동기화

임베딩은 "미리 벡터로 만들어 저장"하는 방식이라, 원본이 바뀌면 벡터도
갱신해야 검색 결과가 최신이 된다.

- 문서 생성 → 임베딩해서 추가
- 문서 수정 → 다시 임베딩해서 갱신(upsert)
- 문서 삭제 → 벡터도 삭제
- **임베딩 모델 교체 → 전체 재임베딩** (벡터 공간이 달라지므로)

실무에서는 생성/수정/삭제 이벤트를 큐(Kafka/SQS, Bull 등)나 스케줄러
배치로 받아 임베딩을 갱신하는 파이프라인을 둔다.

## 파인튜닝과 뭐가 다른가요?

- **파인튜닝**은 지식을 모델 가중치에 새겨 넣는다. 비용이 크고, 갱신할
  때마다 다시 학습해야 하며, 출처를 제시하기 어렵다.
- **RAG**는 지식을 모델 밖(벡터 DB)에 두고 그때그때 검색해 주입한다.
  저렴하고, 문서만 갱신하면 즉시 반영되며, 출처 추적이 된다.
- 최신성·출처·비공개 데이터가 중요하면 RAG, 말투·포맷·특정 작업 능력
  자체를 바꾸고 싶으면 파인튜닝. 둘을 함께 쓰기도 한다.

## RAG를 쓰면 환각이 사라지나요?

완전히 사라지지는 않는다. 검색이 엉뚱한 문서를 가져오거나, 컨텍스트에
없는 내용을 모델이 지어내면 여전히 발생한다. 완화하려면 검색 품질을
관리하고(재현율·정밀도), "컨텍스트에 없으면 모른다고 답하라"는 지시와
출처 표기를 함께 쓴다.
