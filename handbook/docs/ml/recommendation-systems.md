# 추천 시스템 모델 계보

## 콘텐츠 기반 vs 협업 필터링

추천 시스템은 크게 두 갈래로 접근한다.

### 콘텐츠 기반 (Content-based)

유저/아이템의 **속성**(거리, 카테고리, 나이, 관심사 등)을 피처로
만들어 [로지스틱 회귀](logistic-regression.md) 같은 모델로 "이 피처
조합이면 클릭/좋아요할 확률이 얼마"를 예측한다.

```
피처: [distanceScore, categoryMatch, dayMatch, clickScore]
점수 = w1*distanceScore + w2*categoryMatch + w3*dayMatch + w4*clickScore + b
```

- 장점: 신규 유저도 프로필만 있으면 바로 추천 가능(콜드스타트에
  비교적 강함).
- 단점: 피처를 사람이 설계해야 하고, "취향"처럼 사람이 명시적으로
  정의하기 어려운 패턴은 못 담는다.

### 협업 필터링 (Collaborative Filtering)

"이 유저가 뭘 좋아하는지"를 그 유저의 속성으로 계산하는 게 아니라,
**"이 유저와 비슷한 취향을 가진 다른 유저들이 뭘 좋아했는지"**로
추론한다. 유저-아이템 평점표(누가 무엇을 좋아요/패스했는지)를
채우는 문제로 본다.

```
        아이템A  아이템B  아이템C  아이템D
유저1     좋아요    ?      패스    좋아요
유저2      ?      좋아요   좋아요    ?
유저3     좋아요   좋아요    ?      패스
```

`?`가 아직 반응이 없는 칸. "유저1과 취향이 비슷한 유저3이 아이템B를
좋아요했으니, 유저1도 아이템B를 좋아할 확률이 높다"는 식으로 빈칸을
채운다.

**행렬 분해(Matrix Factorization)**가 대표적인 방법 — 넷플릭스가
유명하게 만든 방식. 평점표를 두 개의 작은 행렬로 쪼갠다:

- 유저마다 벡터 하나 (`[0.8, -0.3, 0.5]` — 이 유저의 숨겨진 취향 성향)
- 아이템마다 벡터 하나 (`[0.7, -0.1, 0.6]` — 이 아이템의 숨겨진 특성)
- 두 벡터를 내적하면 예측 점수가 나옴 — 벡터 방향이 비슷할수록
  점수가 높다.

이 벡터들은 사람이 의미를 정의하지 않고, "실제 관측된 좋아요/패스를
가장 잘 설명하는 벡터가 뭘까"를 경사하강법으로 학습해서 찾아낸다.
로지스틱 회귀와 차이는, 로지스틱 회귀는 피처를 사람이 설계하지만
행렬 분해는 벡터 값 자체가 학습 대상이라는 점이다.

- 장점: 사람이 피처를 설계하지 않아도 패턴을 스스로 찾아낸다.
- 단점: **콜드스타트에 약함** — 신규 유저/아이템은 반응 이력이 없어
  "비슷한 대상"을 찾을 방법이 없다. 또한 유저·아이템 수가 충분히
  쌓여야 통계적으로 유의미한 "비슷함"이 잡힌다(수천 명 규모로는
  콘텐츠 기반보다 못할 수도 있음).

**실무에서는 보통 둘을 같이 쓴다** — 콘텐츠 기반으로 후보를 추리고,
그 안에서 협업 필터링 점수로 재정렬하거나, 신규 유저에겐 콘텐츠
기반을 폴백으로 쓰는 하이브리드 구조가 흔하다.

## Two-Tower 임베딩 구조

대규모 추천(유튜브, 틴더 등)에서 표준으로 쓰이는 구조. 유저를 벡터로,
아이템을 벡터로 **각각 독립적인 신경망(tower)**으로 임베딩한 뒤,
두 벡터의 내적(유사도)으로 궁합을 계산한다.

```
유저 정보 → [유저 타워(신경망)] → 유저 벡터 ┐
                                         ├─ 내적(유사도) → 점수
아이템 정보 → [아이템 타워(신경망)] → 아이템 벡터 ┘
```

핵심 이점은 **후보 생성(retrieval) 단계에 쓸 수 있다는 것** — 전체
아이템(수십억 개)을 다 스코어링하는 대신, 미리 계산해둔 아이템
벡터들 중 유저 벡터와 가장 가까운 것들을 벡터 검색(ANN)으로 빠르게
찾아낸다. 사람 대 사람 매칭(데이팅 앱 등)에도 같은 구조가 표준이다.

## Wide & Deep (Google)

단순한 선형 부분(Wide, 우리가 만든 로지스틱 회귀와 같은 구조)과
신경망 부분(Deep, [여러 층 쌓은 모델](neural-networks.md))을 하나의
모델에 합친 구조.

- **Wide**: "이 조합이면 확실히 그렇다"는 명시적 규칙/기억
  (memorization)에 강하다 — 예: "카테고리=러닝 AND 요일=화요일"
  조합을 직접 피처로 넣으면 그 조합을 정확히 기억한다.
- **Deep**: 명시적으로 넣지 않은 피처 조합도 층을 통해 스스로
  발견한다(generalization) — 예: 학습 데이터에 없던 새로운 조합에도
  어느 정도 일반화된 예측을 한다.

## 실무 파이프라인 — 2단계 (후보 생성 + 랭킹)

대규모 서비스는 전체 아이템을 다 스코어링하지 않고 2단계로 나눈다.

1. **후보 생성(Candidate Generation)** — Two-Tower 임베딩 검색 등으로
   전체 중 "볼 만한 것 같은" 후보 수백~수천 개를 빠르게 추림.
2. **랭킹(Ranking)** — 추려진 후보만 훨씬 무거운 모델(신경망, 피처
   수백 개)에 넣어 정교하게 순위를 매김. 실무에서는 좋아요 확률뿐
   아니라 댓글/공유/체류시간 확률까지 **하나의 모델이 동시에
   예측**하는 멀티태스크 학습을 흔히 쓴다.

## 실제 사례

- **틴더**: 초창기엔 체스 레이팅에서 따온 Elo 점수(상대방 스와이프
  반응으로 매기는 단순 인기도)를 썼다가, 이후 그래디언트 부스팅
  트리 계열 모델로 여러 신호(활동 시간대, 최근 활동성 등)를 조합하는
  다차원 추천 엔진으로 전환했다. 핵심 신호 중 하나는 **"서로 좋아할
  확률"** — 내가 좋아할 확률뿐 아니라 상대도 나를 좋아할 확률까지
  같이 예측해 매칭 가능성이 높은 사람을 우선한다(단방향 예측만 하는
  콘텐츠 기반 모델과의 차이점).
- **인스타그램**: 위에서 설명한 2단계(후보 생성 + 랭킹) 파이프라인을
  씀. 후보 생성엔 Two-Tower 임베딩, 랭킹엔 멀티태스크 딥러닝 모델을
  사용한다.

## 온라인 학습과 실무 트레이드오프

"방금 한 행동이 바로 다음 추천에 반영되는 것"을 실시간(온라인)
학습이라 부르는데, 두 층위를 구분해야 한다.

- **유저 프로필(피처)의 실시간 갱신**: 방금 좋아요한 이력을 다음
  요청부터 즉시 반영하는 것 — DB에서 매번 최신 이력을 조회하면
  자연히 실시간이 된다. 구현이 쉽고 리스크도 낮다.
- **모델 가중치 자체의 실시간 갱신**: 좋아요/패스가 들어올 때마다
  그 한 건으로 경사하강법 한 스텝을 즉시 실행해 전역 가중치를
  바로 고치는 것. 한 건짜리 업데이트는 노이즈에 매우 민감하고,
  가중치가 **모든 유저에게 공유**되는 구조라면 한 유저의 특이한
  패턴이 즉시 다른 모든 유저의 추천에도 영향을 준다.

그래서 실무에서는 보통 "모델 가중치는 배치로 주기적(몇 시간~하루)
재학습, 그 사이엔 프로필(피처)만 실시간 반영"하는 절충안을 쓴다.

## 자주 나오는 질문

**Q. 콜드스타트 문제는 어떻게 대응하나요?**
신규 유저/아이템은 반응 이력이 없어 협업 필터링이 무력화된다.
초기엔 콘텐츠 기반(속성 기반) 추천이나 인기도 기반 추천으로
폴백하고, 이력이 쌓이면 점차 협업 필터링 비중을 높이는 하이브리드
전략을 쓴다.

**Q. 피처 엔지니어링 시 미래 데이터 leakage를 어떻게 막나요?**
학습 데이터의 각 샘플(예: impression 시점)에 대해, 그 시점
**이전**의 이력만으로 피처(과거 클릭 점수, 과거 카테고리 선호 등)를
계산해야 한다. 시점 이후의 정보가 섞이면 학습 때는 성능이 좋아
보이지만 실제 서빙 시점엔 재현 불가능한 성능(과적합보다 더 심각한
데이터 leakage)이 나온다.
