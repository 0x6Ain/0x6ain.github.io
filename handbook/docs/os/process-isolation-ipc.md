# 프로세스 격리, IPC, 커널/유저 모드

## 프로세스는 왜 독립된 주소 공간을 가지는가

프로세스는 실행 중인 프로그램의 인스턴스이며, 각자 독립된
**주소 공간(Address Space)**을 가져서 다른 프로세스의 메모리를 직접
들여다보거나 건드릴 수 없다.

**이유는 오류 격리(Fault Isolation)다.** 모든 프로세스가 메모리를
공유한다면:

- 한 프로세스의 버그(잘못된 포인터 접근 등)가 다른 프로세스의 데이터를
  덮어써서 시스템 전체가 연쇄적으로 망가질 수 있다.
- 악의적인 프로그램이 다른 프로세스의 민감한 데이터(비밀번호, 개인정보
  등)를 훔쳐볼 수 있다 — 보안 문제.

OS는 **가상 메모리(Virtual Memory)**로 각 프로세스가 마치 메모리를
독점하는 것처럼 착각하게 만든다. 실제로는 물리 메모리를 잘게 쪼개
나눠 쓰지만, 프로세스 입장에서는 자기 혼자 메모리를 다 쓰는 것처럼
동작한다.

## IPC (Inter-Process Communication)

격리된 프로세스끼리도 서로 데이터를 주고받아야 할 때가 있다(예: 웹
브라우저와 다운로드 매니저 프로세스). OS는 격리를 유지하면서도
필요한 소통만 허용하는 공식 통로를 제공한다.

| 방식 | 설명 |
|---|---|
| **파이프(Pipe)** | 한 프로세스의 출력을 다른 프로세스의 입력으로 연결. 셸의 `ls \| grep test`가 대표 예시 |
| **공유 메모리(Shared Memory)** | 특정 메모리 영역을 두 프로세스가 함께 접근하도록 허용. 가장 빠르지만 동시 접근(동기화)은 프로그래머가 직접 처리해야 함 |
| **소켓(Socket)** | 네트워크 통신처럼 메시지 교환. 같은 컴퓨터 안에서도(유닉스 도메인 소켓), 다른 컴퓨터와도 사용 가능 |
| **시그널(Signal)** | 간단한 이벤트 알림. `Ctrl+C` → `SIGINT`가 대표 예시 |
| **메시지 큐(Message Queue)** | 메시지를 큐에 넣고 빼며 비동기적으로 통신 |

핵심은 프로세스가 서로 직접 통신하는 게 아니라 **커널이 중재자**
역할을 한다는 점이다. 프로세스가 통신하고 싶으면 **시스템 콜(System
Call)**을 호출하고, 커널이 이를 검증한 뒤 안전하게 데이터를
전달한다.

## 커널 모드 vs 유저 모드

프로세스가 IPC나 하드웨어 접근을 커널을 거쳐서만 할 수 있는 이유는
CPU가 하드웨어적으로 실행 권한을 두 단계로 나눠두었기 때문이다.

- **유저 모드(User Mode)**: 일반 프로세스가 실행되는 모드. 메모리
  주소 직접 조작, 디스크 직접 쓰기, 다른 프로세스 메모리 접근 같은
  **특권 명령어(Privileged Instruction)**는 실행 자체가 막혀 있다.
- **커널 모드(Kernel Mode)**: OS(커널)만 접근 가능한 모드. 모든
  하드웨어를 자유롭게 제어할 수 있다.

프로세스가 하드웨어 자원이 필요하면 시스템 콜을 호출하고, 이때 CPU가
유저 모드에서 커널 모드로 전환된다. 커널이 요청을 검증한 뒤 안전하게
처리하고 다시 유저 모드로 복귀한다.

**왜 이렇게 나눠두었나**

1. **보호(Protection)**: 버그 있는 프로그램이 하드웨어를 직접
   조작하면 디스크를 망가뜨리거나 다른 프로세스 메모리를 훼손할 수
   있다.
2. **자원 중재**: CPU, 디스크 같은 공유 자원을 여러 프로세스가 안전하게
   나눠 쓰려면 커널이 중간에서 조율해야 한다.
3. **보안**: 악성 프로그램이 시스템 전체를 장악하는 것을 막는다.

즉 "빠르게 직접 처리" 대신 "안전하게 검증받고 처리"를 선택한
것이다.

## 시스템 콜이 잦으면 왜 느려지는가

시스템 콜 한 번을 처리하는 과정은 대략 다음과 같다.

1. 유저 모드 → 커널 모드 전환, 현재 레지스터 값 저장
2. 커널이 요청을 검증
3. 작업 수행 후 커널 → 유저 모드 복귀, 레지스터 복원

이 모드 전환 자체가 일반 함수 호출보다 수십~수백 배 느릴 수 있다.
파일을 한 글자씩 `read()`로 읽는 것처럼 시스템 콜을 아주 자주
호출하면, 실제 작업(디스크에서 몇 바이트 읽기)보다 모드 전환
오버헤드가 누적되어 훨씬 비효율적이다.

**대응 방법**: 시스템 콜 호출 횟수 자체를 줄이는 **버퍼링/배치
처리**가 표준 해법이다. 예를 들어 `read()`를 1바이트씩 부르는 대신
수 KB 단위 버퍼로 한 번에 읽어와 메모리에서 처리하면(대부분의 언어
표준 라이브러리 I/O가 내부적으로 이렇게 동작한다), 시스템 콜 횟수를
데이터 크기와 무관하게 상수에 가깝게 줄일 수 있다.
