# 프로세스/스레드 메모리 구조와 가상 메모리, 페이지 교체

## 프로세스 vs 스레드

- **프로세스**: 실행 중인 프로그램. 코드, 데이터, 힙, 스택으로 이루어진 독립된 메모리 공간을 가진다.
- **스레드**: 프로세스 내부의 실행 흐름 단위. 같은 프로세스의 스레드들은 **코드/데이터/힙을 공유**하지만, **스택만은 각자 따로** 가진다.

### 스택을 스레드마다 따로 두는 이유

스택에는 함수 호출 시 생기는 지역 변수, 리턴 주소, 매개변수가 쌓인다. 즉 "지금 어떤 함수를 실행 중이고 지역 변수는 뭐고 리턴하면 어디로 가는지"라는 **실행 문맥** 자체가 스레드마다 완전히 다르다. 스택을 공유하면 스레드 A와 B의 함수 호출 흐름이 뒤섞여 논리적으로 실행이 불가능해진다. 그래서 스택은 스레드마다 독립적으로 존재해야 한다.

### 힙을 공유하는 이유

스레드를 나누는 목적 자체가 "하나의 작업을 여러 흐름이 나눠 처리하되 결과는 공유"하기 위함이다. 힙까지 스레드마다 독립시키면 사실상 프로세스와 다를 게 없어져서, 스레드라는 개념의 존재 의의(가벼운 자원 + 데이터 공유)가 사라진다. 대신 공유의 대가로 발생하는 동기화 문제(race condition)는 뮤텍스/세마포어 같은 도구로 별도 해결한다.

### 코드 영역은 왜 동기화가 필요 없는가

코드 영역은 실행 파일이 메모리에 로드된 것으로, 실행 중 절대 바뀌지 않는 **읽기 전용(read-only)** 데이터다. Race condition은 기본적으로 누군가 **쓰기(write)** 를 할 때 발생한다. 여러 스레드가 동시에 읽기만 하면 서로 간섭할 일이 없다.

| 영역 | 공유 | 읽기/쓰기 | 동기화 필요? |
|---|---|---|---|
| 코드 | O | 읽기 전용 | 불필요 |
| 힙 | O | 읽기+쓰기 | 필요 |
| 스택 | X (개별) | 읽기+쓰기 | 애초에 공유 안 하니 불필요 |

## 컨텍스트 스위칭

CPU 코어 수는 한정적인데 실행할 프로세스는 많으므로, OS는 각 프로세스에게 짧은 시간(타임 슬라이스)씩 CPU를 나눠준다. 타임 슬라이스가 끝나거나 I/O 요청으로 CPU를 반납하면, OS는 다음 프로세스에게 CPU를 넘긴다. 이렇게 CPU를 쓰던 프로세스(혹은 스레드)가 바뀌는 것이 **컨텍스트 스위칭**이다.

### 무엇을 저장/복원하는가 (PCB)

레지스터는 CPU 내부에 존재하는 아주 작고 빠른 저장공간으로, 현재 계산 중인 값과 **PC(Program Counter, 다음 실행할 명령어 주소)** 등이 담긴다. 문제는 레지스터가 CPU에 하나뿐이라, 다른 프로세스가 CPU를 넘겨받는 순간 그 값을 덮어써버린다는 점이다.

그래서 프로세스가 CPU를 뺏기기 직전, OS는 레지스터 값들이 사라지기 전에 **PCB(Process Control Block)** 라는 구조체에 복사해서 RAM에 저장(save)해두고, 나중에 그 프로세스가 다시 CPU를 받으면 저장해둔 값을 레지스터에 다시 채워 넣어(restore) 이어서 실행한다.

참고로 힙/코드/데이터는 RAM의 특정 주소 공간에 이미 자리 잡고 있으므로, 프로세스가 CPU를 뺏겨도 그 내용은 그대로 남아있다. 별도로 저장할 필요가 없는 것은 레지스터뿐이다.

### 프로세스 전환이 스레드 전환보다 비싼 이유

레지스터/PC 저장·복원은 프로세스든 스레드든 공통으로 필요하다. 하지만 **프로세스 전환**은 여기에 더해:

- 프로세스 A의 메모리 공간(코드/데이터/힙/스택)에서 B의 메모리 공간으로 완전히 갈아끼워야 하므로, MMU가 참조하는 **페이지 테이블** 자체를 교체해야 한다.
- **TLB(주소 변환 캐시)** 도 플러시해야 한다. A와 B는 주소 체계가 완전히 다르므로 A 때 캐싱해둔 변환 결과가 B에게는 쓸모없기 때문이다. 이후 B는 캐시 미스가 이어지며 느려진다.

반면 같은 프로세스 안의 **스레드 간 전환**은 코드/데이터/힙을 어차피 공유하므로 페이지 테이블을 바꿀 필요가 없고, TLB도 플러시할 필요가 없다. 레지스터/PC/스택포인터만 바꿔치기하면 끝난다.

| 전환 | 레지스터/PC | 페이지 테이블 교체 | TLB flush |
|---|---|---|---|
| 스레드 간 | O | X | X |
| 프로세스 간 | O | O | O |

## 가상 메모리

### 왜 필요한가

프로세스마다 실제 물리 주소를 직접 쓰게 하면 두 가지 문제가 생긴다.

1. **충돌 문제**: 여러 프로세스가 같은 물리 주소를 쓰려고 하면 서로 덮어쓴다. 컴파일 시점에는 어떤 프로세스가 어느 물리 주소를 배정받을지 알 수 없다.
2. **침범/보안 문제**: 프로세스 간 격리가 없어서, 한 프로세스가 다른 프로세스의 물리 영역을 직접 건드려 오염시킬 수 있다.

**가상 메모리**는 모든 프로세스에게 "0번부터 시작하는 나만의 메모리 공간을 가진 것처럼" 보이게 한다. 이 가상 주소를 실제 물리 주소로 변환하는 작업은 **MMU**가 **페이지 테이블**을 참조해서 수행한다. 그 결과:

- 프로세스마다 독립된 주소 공간처럼 보여서 코드 작성 시 물리 주소를 신경 쓸 필요가 없다.
- OS가 페이지 테이블로 "이 프로세스는 이 물리 영역만 접근 가능"하게 강제해서 프로세스 간 침범을 막는다.

### 물리 메모리보다 큰 가상 주소 공간이 가능한 이유

가상 주소 공간의 크기와, 그중 실제로 물리 메모리에 채워져 있는 양은 별개다. 지금 당장 쓰지 않는 부분은 물리 메모리에 올리지 않아도 된다.

- 프로세스가 아직 물리 메모리에 없는 가상 주소에 접근하면 **페이지 폴트(Page Fault)** 가 발생하고, OS는 그때 디스크의 **스왑 영역(swap space)** 에서 해당 데이터를 물리 메모리로 가져온다.
- 물리 메모리가 부족해지면, 당분간 안 쓰는 페이지를 디스크로 밀어내고(swap out) 자리를 비운다.
- 페이지 테이블에는 "이 가상 주소는 지금 물리 메모리에 없고 디스크의 이 위치에 있다"는 정보가 기록되어 있어, 페이지 폴트 시 OS가 정확히 어디서 데이터를 가져올지 알 수 있다.

디스크(수백GB~TB)가 물리 RAM(수GB~수십GB)보다 훨씬 크기 때문에 체감상 거의 무한한 메모리처럼 느껴지는 것뿐이며, 디스크도 유한한 자원이라 다 차면 OOM 같은 문제가 발생한다.

## 스래싱(Thrashing)

물리 메모리가 부족한 상태에서 여러 프로세스가 동시에 많은 페이지를 요구하면, OS는 계속 페이지를 디스크와 RAM 사이로 교체하게 된다. 디스크 접근은 RAM 접근보다 수만 배 느리기 때문에, CPU가 실제 계산보다 페이지를 나르는 데 더 많은 시간을 쓰게 되고 시스템이 거의 멈춘 것처럼 느껴진다. 이 현상을 **스래싱**이라 부른다.

### 대응 방법

스래싱은 물리 메모리가 감당하지 못할 만큼 많은 프로세스가 동시에 페이지를 요구해서 생긴다. 그래서 OS는 **동시에 메모리에 올라가는 프로세스 개수(다중프로그래밍 정도)를 제한**한다. 일부 프로세스를 통째로 스왑아웃시켜, 남은 프로세스들이 충분한 페이지를 확보하도록 한다. 이 판단에 쓰이는 방법 중 하나가 **워킹셋(Working Set) 모델**로, 각 프로세스가 최근에 실제로 자주 쓰는 페이지 집합을 추적해서 그것조차 다 못 올려줄 것 같으면 해당 프로세스를 실행 후보에서 제외한다.

| 방법 | 성격 |
|---|---|
| 물리 메모리 증설 | 하드웨어적 해결 (근본 처방) |
| 동시 실행 프로세스 수 제한 (워킹셋 기반) | OS 스케줄링 레벨 해결 (실질적으로 사용) |

프로세스 수를 제한하면 처리량(throughput)은 줄지만 안정성은 확보되는 트레이드오프가 있다.

## 페이지 교체 알고리즘

물리 메모리가 꽉 찼을 때 어떤 페이지를 디스크로 내보낼지 정하는 알고리즘이 필요하다.

- **FIFO**: 먼저 들어온 페이지부터 내보낸다. 실제 접근 패턴을 반영하지 못해 잘 쓰이지 않는다.
- **LRU (Least Recently Used)**: 가장 오랫동안 안 쓰인 페이지부터 내보낸다. 최근에 쓴 데이터는 앞으로도 쓰일 가능성이 높고, 오래 안 쓴 데이터는 앞으로도 안 쓰일 가능성이 높다는 **지역성(Locality)** 경험칙에 근거한다. Redis 같은 캐시 시스템의 eviction 정책도 같은 아이디어를 사용한다.
- **LFU**: 가장 적게 쓰인 페이지부터 제거.
- **Optimal**: 미래를 안다고 가정하고 이상적으로 제거하는 이론적 기준점.

### 완벽한 LRU가 실제로는 잘 안 쓰이는 이유

완벽한 LRU를 구현하려면 페이지에 접근할 때마다 정확한 시간(또는 순번)을 기록해야 한다. 프로세스는 초당 수백만~수십억 번 메모리에 접근하므로, 매 접근마다 타임스탬프를 갱신하고 페이지들을 시간순으로 재정렬하는 비용은 하드웨어적으로 감당하기 어렵다.

그래서 실제로는 **근사치(approximation)** 를 쓴다. 대표적으로 **Clock 알고리즘(Second-Chance)**:

- 각 페이지에 정확한 시간 대신 1비트짜리 **참조 비트(reference bit)** 만 둔다. 접근하면 1로 세팅.
- 교체 후보를 찾을 때 시계 바늘처럼 페이지들을 순회하며, 참조 비트가 0이면 내보내고 1이면 0으로 바꾼 뒤 다음으로 넘어간다.
- 정확히 언제 썼는지는 모르지만 "최근에 한 번이라도 안 쓰였는지"는 대략 알 수 있다. 정확도는 낮아지지만 비용은 훨씬 저렴하다.

이는 OS 설계 전반에 깔린 철학과 맞닿아 있다: **완벽함보다 실용성**, 즉 정확성과 오버헤드의 트레이드오프에서 "충분히 괜찮은 근사치를 싸게 얻는" 쪽을 택한다.

### 참조 비트를 하드웨어(MMU)가 세팅하는 이유

참조 비트는 CPU가 메모리를 읽거나 쓸 때마다, 즉 초당 수백만~수십억 번 세팅되어야 한다. 만약 OS(소프트웨어)가 이걸 처리하려면 모든 메모리 접근을 가로채야 하는데, 이는 사실상 모든 명령어 실행을 인터럽트로 도배하는 것과 같아 오버헤드가 극심하다.

반면 MMU는 모든 메모리 접근마다 가상주소→물리주소 변환을 어차피 수행하고 있으므로, 그 과정에서 참조 비트 하나 켜는 것은 회로적으로 거의 추가 비용이 없다.

**원칙**: 매번 일어나는 일(메모리 접근마다 발생하는 참조 비트 세팅)은 하드웨어가 처리해야 싸고, 가끔 일어나는 일(페이지 교체 결정, 컨텍스트 스위칭)은 소프트웨어가 처리해도 괜찮다.
