# 확장성 전략과 CAP 이론

## 수직 확장 vs 수평 확장

시스템 트래픽이 늘어날 때 서버 용량을 늘리는 방법은 두 가지다.

- **수직 확장 (Scale-up)**: 서버 한 대의 CPU/메모리/디스크 스펙을 올린다.
- **수평 확장 (Scale-out)**: 서버 대수를 늘려서 트래픽을 여러 대에 분산한다.

대규모 서비스는 대부분 수평 확장을 선호한다. 이유는 세 가지다.

1. **비용**: 수직 확장은 스펙이 올라갈수록 가격이 기하급수적으로 뛴다. 고성능 서버일수록 프리미엄이 붙기 때문에, 스펙 2배가 가격 2배로 끝나지 않는다.
2. **물리적 한계**: 수직 확장은 무한히 올릴 수 없다. 현존하는 가장 강력한 CPU/메모리도 결국 한계가 있고, 트래픽이 그 한계를 넘으면 대응할 방법이 없다. 반면 수평 확장은 서버를 계속 추가하면 되므로 이론상 한계가 없다.
3. **가용성**: 수직 확장한 서버 한 대가 죽으면 서비스 전체가 다운된다. 수평 확장으로 여러 대에 분산되어 있으면 한 대가 죽어도 나머지가 트래픽을 받아준다.

## 수평 확장의 대가

서버가 여러 대가 되는 순간 데이터를 어떻게 다룰지가 새로운 문제가 된다.

- **데이터 정합성(Consistency) 문제**: 사용자가 서버 A에서 정보를 바꿨는데 다음 요청이 서버 B로 가면, B는 옛날 데이터를 갖고 있을 수 있다. 어느 서버의 데이터가 "진짜 최신"인지 결정해야 하는 문제가 생긴다.
- **상태(state) 관리 복잡도**: 서버가 하나면 메모리에 세션 정보를 그냥 들고 있으면 되지만, 여러 대가 되면 어떤 서버로 요청이 가도 같은 응답을 줄 수 있어야 한다. 그래서 세션을 Redis 같은 외부 저장소로 빼거나, 같은 사용자의 요청을 항상 같은 서버로 보내는 sticky session 전략이 필요해진다.
- **네트워크 오버헤드 & 복잡성 증가**: 서버 간 통신, 로드밸런서, 서비스 디스커버리 등 인프라 자체가 복잡해지고, 어느 요청이 어느 서버를 거쳤는지 추적하는 디버깅도 어려워진다.

즉 수평 확장은 "비용 절감과 무한 확장"을 얻는 대신 "데이터 정합성과 시스템 복잡도"라는 비용을 떠안는 트레이드오프다.

## CAP 이론

분산 시스템(서버가 여러 대로 나뉜 시스템)에는 세 가지 속성이 있다.

- **C (Consistency, 일관성)**: 모든 서버가 항상 같은(최신) 데이터를 보여준다.
- **A (Availability, 가용성)**: 요청하면 항상 응답을 받는다 (에러 없이).
- **P (Partition tolerance, 분단 허용)**: 서버 간 네트워크가 끊겨도 시스템이 계속 동작한다.

CAP 이론의 핵심 주장은 **이 셋을 동시에 완벽하게 만족시킬 수 없다**는 것이다. 그런데 실제로는 P가 선택 사항이 아니다. 분산 시스템에서 네트워크 장애(케이블 끊김, 스위치 고장 등)는 언젠가 반드시 일어나기 때문에, P는 사실상 필수로 놓고 실제 선택은 **C와 A 사이의 트레이드오프**가 된다.

### 네트워크 분단 상황에서의 선택지

서버 A와 서버 B 사이 네트워크가 끊긴 상황에서 A에 쓰기 요청이 들어왔다고 하자.

| 선택 | 동작 | 지키는 것 | 포기하는 것 | 시스템 유형 |
|---|---|---|---|---|
| ① 요청 거부(에러 반환) | B와 동기화되지 않았으니 응답을 안 준다 | C (일관성) | A (가용성) | **CP 시스템** |
| ② 일단 처리하고 응답 | 동기화 안 됐어도 일단 응답해준다 | A (가용성) | C (일관성) | **AP 시스템** |

- **CP 시스템**: 정확성이 생명인 도메인에 적합하다. 예: 은행 거래, 재고 관리. 데이터가 조금이라도 틀리느니 차라리 잠깐 응답을 안 주는 게 낫다.
- **AP 시스템**: 서비스 중단이 더 치명적인 도메인에 적합하다. 예: SNS 좋아요 수, 조회수. 숫자가 잠깐 안 맞아도 서비스가 계속 도는 게 더 중요하다.

## 실무 팁

시스템을 설계할 때 "이 데이터가 틀리면 어떤 일이 벌어지는가"와 "이 서비스가 잠깐 멈추면 어떤 일이 벌어지는가"를 비교해보면 CP/AP 중 어느 쪽이 맞는지 판단하기 쉽다. 하나의 서비스 안에서도 도메인별로 다른 선택을 할 수 있다 (예: 결제 파트는 CP, 알림/카운트 파트는 AP).
