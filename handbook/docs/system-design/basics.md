# 시스템 설계 기본기

시스템 설계 면접(알림 시스템, 채팅, 좋아요 기능, URL Shortener, 대용량
로그 수집 등)은 정답을 맞히는 문제가 아니라, 요구사항에 맞게
트레이드오프를 설명하는 문제다. 아래 구성 요소들을 조합해 설계를
풀어나간다.

## 자주 쓰이는 구성 요소

- **Cache / Redis** — 자주 조회되지만 자주 바뀌지 않는 데이터를
  메모리에 올려 DB 부하를 줄인다. 자세한 전략은
  [캐시 전략](../redis/redis-caching.md) 참고.
- **Kafka / SQS** — 요청을 즉시 처리하지 않고 비동기로 처리해
  트래픽 스파이크를 흡수한다. 자세한 내용은
  [Kafka/SQS 기본 개념](../kafka/kafka-basics.md) 참고.
- **DB 분리** — 하나의 DB가 모든 부하를 감당하지 못할 때 나누는
  방법들.
  - **Read Replica**: 읽기 전용 복제본을 두어 조회 트래픽을
    분산한다 (쓰기는 여전히 마스터 하나로 집중).
  - **Sharding**: 데이터를 여러 DB 인스턴스로 나눠 저장한다(예:
    사용자 ID 기준). 쓰기 트래픽도 분산할 수 있지만, 샤드를 넘나드는
    조회/트랜잭션이 복잡해진다.
- **Scale Out** — 서버 한 대의 사양을 올리는 Scale Up 대신, 같은
  사양의 서버를 여러 대로 늘려 [Load Balancer](../network/dns-lb.md)
  로 트래픽을 분산하는 방식. 무중단으로 유연하게 확장할 수 있지만,
  서버 간 상태 공유(세션, 캐시 등)를 별도로 설계해야 한다.

## 설계 예시로 짚어보는 포인트

- **알림 시스템** — 알림 발생과 실제 발송(푸시/이메일)을 분리해
  큐(Kafka/SQS)로 비동기 처리한다. 대량 발송 시 특정 사용자에게
  몰리지 않도록 팬아웃(Fan-out) 방식을 고려한다.
- **채팅 시스템** — 실시간 연결(WebSocket)을 유지하는 서버가 여러
  대일 때, 서로 다른 서버에 붙은 두 사용자를 어떻게 연결할지가
  핵심이다. Redis Pub/Sub이나 별도 메시지 브로커로 서버 간 메시지를
  중계한다.
- **좋아요 기능** — 단순해 보이지만 동시성이 핵심이다. 카운트를
  DB에서 직접 증감시키기보다, [Atomic
  Update](../database/concurrency.md)나 Redis 카운터로 처리하고
  주기적으로 DB에 반영(배치)하는 방식을 고려할 수 있다.
- **URL Shortener** — 짧은 키를 생성하는 방식(랜덤 vs 순차 ID
  인코딩)과, 조회가 압도적으로 많은 워크로드이므로 캐시 계층을
  어디에 둘지가 핵심이다.
- **대용량 로그 수집** — 로그를 즉시 DB에 쓰지 않고 큐에 적재한 뒤
  배치로 모아 저장소(S3, 데이터 웨어하우스 등)에 적재하는 파이프라인
  구조가 일반적이다.
