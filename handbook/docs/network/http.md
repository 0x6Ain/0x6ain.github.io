# HTTP와 HTTPS

## HTTP 1.1 / HTTP2 / HTTP3

- **HTTP/1.1** — 커넥션당 한 번에 하나의 요청/응답만 처리(Head of
  Line Blocking). Keep-Alive로 연결은 재사용하지만, 파이프라이닝은
  실질적으로 잘 쓰이지 않는다.
- **HTTP/2** — 하나의 TCP 연결 위에서 여러 요청/응답을 **멀티플렉싱**
  한다. 헤더를 압축(HPACK)하고, 서버가 클라이언트 요청 없이도 리소스를
  미리 보낼 수 있다(Server Push). 다만 TCP 계층에서 패킷 손실이
  발생하면 그 연결 위의 모든 스트림이 영향을 받는 문제(TCP 레벨
  HOL Blocking)가 남아 있다.
- **HTTP/3** — 전송 계층을 TCP 대신 **QUIC(UDP 기반)**으로 바꿔, 한
  스트림의 패킷 손실이 다른 스트림에 영향을 주지 않도록 한다. 연결
  수립 시간도 더 짧다.

## HTTPS는 어떻게 안전한가요?

HTTPS는 HTTP 통신을 **TLS**로 감싸 암호화한 것이다.

1. **핸드셰이크**: 클라이언트와 서버가 사용할 암호화 방식(Cipher
   Suite)을 합의하고, 서버는 인증서(공개키 포함)를 클라이언트에게
   전달한다.
2. **인증서 검증**: 클라이언트는 신뢰할 수 있는 CA(인증기관)가
   서명했는지 확인해, 접속한 서버가 진짜 그 도메인의 서버인지
   검증한다 (중간자 공격 방지).
3. **키 교환**: 비대칭키(공개키/개인키) 방식으로 세션에서 사용할
   대칭키를 안전하게 교환한다.
4. **대칭키 암호화 통신**: 이후 실제 데이터는 교환한 대칭키로
   암호화해 주고받는다. 비대칭키 암호화는 느리기 때문에, 키 교환에만
   쓰고 실제 데이터 전송은 빠른 대칭키를 사용한다.

즉 **신뢰할 수 있는 상대인지 검증(인증서)**과 **통신 내용을
암호화(TLS)** 두 가지가 합쳐져 안전성을 보장한다.

## TLS

Transport Layer Security. 이전 버전인 SSL을 대체한 프로토콜로,
위에서 설명한 핸드셰이크·인증서 검증·암호화 통신을 담당한다.
